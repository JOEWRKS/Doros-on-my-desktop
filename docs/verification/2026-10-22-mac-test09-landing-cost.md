# Mac test09 — 착지 발 판정의 직렬 대기 감소

## 사용자 결정과 경계

사용자는 새 로그가 생성되지 않는다고 보고했고, 추가 로그를 제공하지 않겠으니
담당자가 기존 근거로 수정하라고 명시했다. **추가 로그·재조작은 요청하지 않는다.**
상단 이동 개선은 기존 사용자 보고로 유지한다. 남은 증상은 바닥 접촉·퍼짐의 끊김이다.
기존 schema1 파일 두 개를 새 실행 증거로 재사용하지 않았다.

## 확인한 원인과 최종 변경

Windows에서 Mac의 실제 `R104DesktopController`를 별도 headless 프로세스로 실행했다.
내장 화면 1470×956, 100/125/150%, 밀도1/2, 머리 잡기→상단 이동→놓기→강한 착지를
조건마다3회 입력했다. 입력은 코드로 공급했으며 실제 Mac 마우스 조작이 아니다.
16ms 시뮬레이션 간격이며 실시간/장시간 soak도 아니다.

착지에서는 픽셀당8×8 샘플을 쓴다. 최종 표시 이미지는 기존 bounded worker들로
병렬 계산하지만, 그 전에 두 번 필요한 발바닥 위치 판정은 필요한 행을 UI 호출자
혼자 계산했다. 호스트에서 퍼짐 갱신 비용이 증가하는 경로를 재현했다.
**이것은 확인된 코드 병목이며 사용자의 M2 끊김 전부의 단독 원인 확정은 아니다.**

최종 변경은 Mac 전용 `HighResolutionGrabRaster.cs`의 작업 분할뿐이다.

- 발 판정은 여전히 한 행씩 아래에서 위로 진행하고, 같은2-DIP 밴드에서 멈춘다.
- 8×8 샘플이 필요한 폭32픽셀 이상 행만 열 단위로 기존 worker에 나눠 맡긴다.
- 표시 렌더의 픽셀 수·샘플 위치·보간 산술·alpha 임계값은 변경하지 않는다.
- 새 스레드/프레임 캐시/이미지 버퍼를 추가하지 않는다. 기존 bounded queue와
  작업 참조 해제 정책을 사용하며, 활성 픽셀 작업이 끝난 뒤에만 반환한다.
- 작은 행과 일반2×2 행은 기존 호출자 직렬 경로를 유지한다.
- Windows App/Core/Portable/원화/설정/설치본 및 물리·퍼짐 곡선은 변경하지 않았다.

병렬화는 총 CPU 작업량 감소와 같은 뜻이 아니다. 작업 dispatch 할당/스케줄링 비용은
추가된다. 실제 M2의3worker와 호스트의 worker 수/코어 특성도 다르므로 전력·CPU·
장시간 메모리 개선 또는 모든 착지의16ms 이하를 주장하지 않는다.

## 성능 근거

`artifacts/macos/landing-cost-20261022/`:

- `baseline-host/`: 렌더 수정 전 불변 호스트 빌드.
- `before-final.json` vs `parallel-sole-after.json`: 각각6조건×480=2,880프레임.
- `comparison-parallel.json`: 픽셀 SHA256, 위치, 발/가시 경계, platform 상태 모두 불일치0.
- 성능 선택 기준은 첫 cycle을 제외한 나머지2cycle 중 spread>0이고 이전 프레임과
  픽셀이 달라진 구간. 측정값을 보고 느린 프레임만 선택한 것이 아니다.
- 평균 갱신 시간(ms):

| 크기 / 밀도 | 이전 | 수정 | 감소 |
| --- | ---: | ---: | ---: |
| 100 / 1 | 8.00 | 6.44 | 19.5% |
| 100 / 2 | 21.08 | 14.73 | 30.1% |
| 125 / 1 | 10.54 | 8.28 | 21.4% |
| 125 / 2 | 31.24 | 20.30 | 35.0% |
| 150 / 1 | 14.47 | 10.05 | 30.5% |
| 150 / 2 | 40.65 | 27.74 | 31.8% |

150/2의 p95는48.86→34.59ms, 최대49.61→38.97ms였다. 아직16ms보다 높다.
100/2의 해당 구간 process CPU 합계는2562.5→3250ms로 증가했고, 다른 조건도
CPU 합계가 일관되게 감소하지 않았다. 따라서 "CPU 사용량 해결"로 보고하지 않는다.
비교는 순차 호스트 실행이며 OS 외부 부하를 통제한 M2 성능 실험이 아니다.

## 채택하지 않은 시도

아래 후보는 픽셀 동일성만으로 채택하지 않았다. 일관된 처리시간 개선이 확인되지
않아 **최종 코드에서 제거했다.** 중간 설명은 작업 중 가설이며 최종 해결 목록이 아니다.

- sole 단일 alpha 채널 샘플러: `alpha-after.json`, `sole-alpha.trx`.
- inverse-spread 행 lookup/alpha uniform 최적화: `lookup-after.json`,
  `fast-sole-after.json`, `after-final.json`, `spread-lookup.trx`.
- 256bit 비가속 환경에서 명시적인 두128bit 벡터: `before-noavx.json`,
  `after-noavx.json`, `comparison-noavx.json`. 일부 구간 악화. 실제 ARM 시험 아님.
- 첫 probe의 낙하 높이가 강한 착지 조건에 못 미친 `before.json`은 강한 착지 근거가
  아니다. probe에 IsExtremeLanding 미발생 실패 검사를 추가했다.

최종 렌더 변경에는 위 lookup 버퍼/alpha 최적화/벡터 분기/테스트용 옵션이 없다.

## 회귀 검사와 미확인

- Raster69/69 (`mac-raster-final.trx`): 신규10조건은27자세씩, 총270표시 이미지와
  270발 판정 scratch의 **전체 BGRA 바이트**를 직렬/병렬로 비교한다.
- Mac285/285 (`mac-test09-final.trx`).
- Python 패키징11 + launcher3 =14개 검사. launcher는12시나리오를 stub 실행한다.
- 로그 생성 실패 원인 자체는 사용자 Mac에서 미확정이다. 코드상 쓰기 실패가 내부
  Failure로만 남던 경로를 stderr/오류창에 노출하고, 커맨드는 실행 전 쓰기 가능 여부와
  앱 stdout/stderr를 별도 파일에 남긴다. 중복 실행도 명시 오류로 표시한다.
  초기화 전에 진단을 생성하고, 초기화 실패는 조기 종료로 기록한다.
- Windows에서 실제 LaunchServices/권한/Gatekeeper/커맨드 파일 생성은 검증하지 못했다.
- M2 AppKit 표시/upload/GPU 지연, 착지 체감 해결, 외장 클램쉘, 장시간 메모리는
  **NOT_TESTED**. 이 문서는 완전 해결/사용자 수락 판정이 아니다.
- 원화·동작·속도 변경 없음은 소스 범위 및 비교한2,880프레임 근거이며, 모든 가능한
  맥 화면/동작 조합의 직접 검수를 뜻하지 않는다.
