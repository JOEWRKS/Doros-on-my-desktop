# r73/r74 체감 개선 실패 · r75 갱신 주기 후보

## 판정과 보존 범위

- r73 사용자: “비슷함”. r74 사용자: “흔들떄랑 떨어질 때 렉이 그대론데”. 두 버전 모두 버벅임 해결 **실패/미수락**이다. 준비·할당 비용의 일부 감소를 제품 성능 통과로 확대하지 않는다.
- r70 수락 원화, 눈/볼/머리 끝/몸/발 형태와 간식 속도 유지. 설치본·사용자 설정 변경 없음.
- r75는 Release 후보 게시 및 자동 검사까지 완료. 사용자 “ㄱㄷ”에 따라 **교체·실행·측정 시작 안 함**. 마지막 프로세스 확인은 정상 투명1.5배 r74 PID108504, Responding=true였다. 사용자 준비 전 추가 입력/재실행 없음.

- 실제 잡기 중 새 raster 생성은 일부4초 구간111회,6초 구간186회였다. 낮은 최대 지연만 보고 연속 동작이 부드럽다고 판정할 수 없다. 사용자 체감은 여전히 비슷했다.

## r75 원인 경로와 수정

기존 PetLoop는 DispatcherTimer16ms를 사용했다. WPF는 Tick 처리 뒤 Restart에서 다음 due time을 현재 시각+Interval로 잡는다. 따라서 동기 렌더 작업 시간에 추가16ms 대기가 붙는 구조다. [WPF 공식 소스](https://raw.githubusercontent.com/dotnet/wpf/main/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/DispatcherTimer.cs)의 FireTick/Restart로 확인했다. 이것을 모든 지연의 유일한 원인이라고 단정하지 않는다.

- production timer를 CompositionTarget.Rendering 기반으로 변경. 동일 RenderingTime은 한 번만 처리하며 중첩 Tick을 막는다. Start/Stop 중복 구독 방지·Stop 시 해제.
- PetLoop의 실제 경과시간 기반 물리/보행 계산은 그대로. 고정 delta나 원화 해상도/샘플 품질/속도 저하로 맞추지 않았다.
- 명시적 성능 기록 옵션에서 실제 PetLoop 시작 간격/작업 시간 `ticks`를 별도 저장. 기존 WPF `frames` 콜백과 분리하여 중복 콜백을 동작 FPS로 오해하지 않도록 했다. 기록 중 디스크 IO 없음.
- 최초 테스트 빌드에서 RenderingEventArgs 생성자가 비공개라 CS1729 발생. 테스트의 가짜 이벤트 생성만 비공개 생성자 반영으로 수정했고 재빌드 통과했다.
- `artifacts/render-cost-20261019-r75/tests/loop.trx`: 261개 통과. 주기 중복/중첩/정지/재시작/예외, 기존 잡기·놓기·발판·볼·앉기·수면·간식 등의 입력 주입 회귀 검사. 실제 OS 드래그 검수가 아니다.
- `tests/pixels.trx`: 3개 통과. `frames/costs.json`의5크기(1/1.1/1.25/1.35/1.5)×6종×12 =360개 원래 r72 변경 전 픽셀 해시 일치, 발 접촉 밴드/불변 Bitmap 검증 및 역변환/볼 곡선 검증. 저장 시트 직접 시각 열람을 했다는 주장은 하지 않는다.
- 게시 App DLL과 검사 대상 DLL SHA256 일치:
  `BFDDB5AE1A1E9162113034CA52CF60B64EBAE0AEA9C4B99C6CB8B610F671EDF9`.
- Core DLL SHA256은 수락 r70과 동일:
  `2F45BC49FD9E58B8B5716E2F92F3E9641CCEEB975C52C08F2B31CA28BDF90888`.
