# Mac test07 로그 분석 및 진단 안내 실패 보고서

작성: 2026-10-22. 대상: 사용자가 전달한 두 boundary JSONL, 현재 test07 코드,
해당 진단을 안내한 이 대화. 이번 요청은 분석·결과 보고이며 앱 수정·재배포는 하지 않았다.

## 1. 결론

1. **로그는 생성됐다.** 첫 파일은 조기 종료, 두 번째는 90초 진단 정상 완료다.
2. **상단 이동 제한의 직접적인 실패 지점을 확인했다.** 내부 좌표는 위로 움직이지만
   네이티브 창의 실제 위쪽 좌표는 Y=33에서 제한된다. 요청 Y<33인 37개 표본 전부
   실제 Y=33이다. 모델의 이동 범위를 더 넓혀 해결할 문제가 아니다.
3. **놓은 뒤 낙하 중에도 위치 불일치가 남는다.** 7개 표본에서 모델은 Falling인데
   실제 창은 Y=33에 남아 있다. 이 위치 제한은 낙하 초반 멈칫함의 확인된 기전이다.
   사용자가 말한 모든 렉이 이것 하나 때문이라고 확정한 것은 아니다.
4. 별도로 표본 간격이 최대 0.940초까지 늘어났다. 위치 진단은 프레임별 프로파일러가
   아니므로 렌더·업로드·OS 호출 중 어느 단계의 지연인지, 정지 지속시간이 얼마인지는
   미확정이다. 성능 해결 판정은 하지 않는다.
5. **내 안내에 실행 조건 누락과 상태 설명 오류가 있었다.** 사용자의 이해나 조작
   잘못으로 돌릴 문제가 아니다. 상세 원인과 책임은 6절에 적었다.

## 3. 상단 제한 — 확인된 직접 원인

두 번째 파일 기준:

- 요청된 창 Y가33 미만인37개 표본 → 실제 창 Y는37개 모두33.
- 그 밖의 표본에서 요청/실제 Y 차이는 최대0.852point. X 차이도 전체 최대0.868point다.
  일반 좌표는 약1point 이내로 따라오지만 상단에서만 큰 제한이 생긴다.
- 최대 차이: **34.834221초, 원본69행**, 요청Y=-152.5 / 실제Y=33 / 차이185.5point.
  포인터Y=0.210938, 모델 위치Y=-56.5. 즉 커서는 위에 도달했고 모델도 따라간다.
- 같은 표본의 모델 VisibleTop=54이므로 모델의 가시 상단은 -2.5point,
  네이티브 위치 차이를 적용한 가시 상단은 약183point다. 화면956point의 약19.1%로,
  사용자가 말한 '상단1/5에서 막힘'과 수치상 부합한다.
  이는 로그 지오메트리로 계산한 값이지 실제 화면 픽셀을 측정한 값은 아니다.

현재 연결 구조:

```text
내부 모델 위치
  → 창 요청 위치 = 모델 위치 - (96,96)
  → Quartz→Cocoa 변환 → setFrameTopLeftPoint:
  → 실제 NSWindow frame은 위쪽 Y=33에 제한
  → 모델은 계속 이동하지만 화면은 제한 위치에 남음
```

근거 코드:

- `DesktopPreviewWindow.cs`: Tick에서 모델 진행·그림 업로드 뒤 MoveIfChanged 호출.
- `QuartzDesktop.cs`: MoveIfChanged는 요청 Cocoa 좌표를 기준으로 캐시하고 네이티브 위치를 설정.
  PlacementEvidence는 별도로 실제 NSWindow frame을 읽어 Quartz 좌표로 변환.
- `Presenter.cs`: 가시 형상 측정에 release offset을 포함. 보고서의 가시 상단 계산은
  모델 위치에 해당 geometry를 더하고 실제/요청 창 위치 차이만 보정했다.

**확정 범위:** 요청과 실제 네이티브 위치의 상단 제한 불일치 및 이를 일반 배치 경로에서
보정하지 않는 결함. 원점/화면 높이는 두 자료에서 일치하고 화면 전환도 없었으므로,
test07의 화면 배치 캐시 수정만으로 이 현상을 해결할 수 없었다.

**아직 확정하지 않은 것:** AppKit/Avalonia 내부에서 제한을 적용한 정확한 메서드·정책.
33point는 로그에 보이는 메뉴 막대 높이와 맞지만, 그 일치만으로 특정 API 내부 호출을
추적했다고 주장하지 않는다. Native placement 경로를 수정 대상으로 좁혔으며
물리 속도·캐릭터 형태 변경은 해결책에서 제외한다.

이때 측정된 형상 기준 가시 상단은 모두 약177.5point다. 예를 들어80.580초에는
실제Y=33, 다음81.091초 표본에는 요청Y≈346.97 / 실제Y=347로 내려간다.
모델이 위쪽 제한 구간을 빠져나오기 전까지 화면 위치가 멈춰 있다가 따라오는 기전과
일치한다. 정확한 해제 순간·연속 프레임 이동곡선은0.5초 자료로 복원하지 않는다.

성능 관련 별도 증거:

- 두 번째 파일의 표본 간격 중앙값은 약0.512초, 최대0.940284초다.
- 0.6초 초과 구간6개는14.191 / 28.077 / 28.680 / 66.171 / 71.212 / 71.823초에 끝난다.
  이 표본들은 모두 낙하 또는 착지이며 SceneHealth=FloorFallback이다.
- 전체 Fresh48 / Cached119 / FloorFallback7. 첫 시작 표본을 제외한6개 fallback과
  위 긴 간격이 일치한다. 모니터 목록은 변하지 않았다.
- SceneCache는 유효 장면이 없거나500ms 이상 오래되면 창 발판 대신 바닥만 제공한다.
  fallback의 sceneAge=0은 새 대체 장면의 시각이며 '실제 창 정보가0초로 신선함'이 아니다.
- captureStatus는174개 모두Success지만 마지막 네이티브 조회 상태이므로, 현재 장면의
  신선도나 스케줄링 지연이 없음을 뜻하지 않는다.

**판정:** 상태 갱신 지연/조회 노후화의 추가 증거는 있다. 그러나0.940초를 그대로
단일 프레임 렌더 시간 또는 CPU 정지 시간으로 해석할 수 없다. UI 스케줄링, 렌더,
업로드, 창 이동, 백그라운드 조회 각각의 시간이 없고 원인 순서도 미확정이다.
위치 제한을 고친 후에도 남는 성능 문제는 단계별 시간으로 분리해야 한다.
현재 로그를 다시 같은 방식으로 반복 수집할 이유는 없다.

## 5. 진행 계획의 갱신

1. 상단 이동/낙하의 요청-실제 좌표 불일치를 맥 네이티브 창 배치 계층에서 해결한다.
   범위를 넓히거나 낙하 속도를 바꾸는 우회는 하지 않는다. 실제 위치 제한을 반영하는
   회귀 재현과, 화면 밖 투명 여백/렌더 원점/클릭 좌표가 함께 맞는지 확인한다.
2. 진단 런처는 앱 위치 확인 전에 기록 안내를 먼저 출력하는 현 구조를 정리한다.
   앱 탐색 실패와 기록 시작/완료를 명시적으로 구분하고, 경로를 사용자가 추측하지 않게 한다.
3. 별도 렌더 지연이 남는다면 bounded 단계별 시간 계측을 추가하고 정상 실행과 구분한다.
   같은 반초 로그나 전체 CPU/메모리 검사를 다시 반복하지 않는다.
4. 코드/패키지 수정과 실제 맥 검증을 각각 기록한다. 이번에는 분석·문서만 작성했으며
   해결판/새 다운로드/네이티브 통과를 선언하지 않는다. 추가 사용자 조작은 요청하지 않았다.

### 원인 판정

관찰 가능한 원인은 **계획과 실제 런처의 실행 조건을 최종 사용자 안내에 반영하지 않은
검증·인계 실패**다. `boundary-diagnostic.command`와 README를 확인할 수 있었고,
실제로 코드를 읽은 뒤에도 '앱과 같은 폴더 / 앱 자동 실행 / 커맨드 즉시 종료 /
파일 생성 / 기록 완료'를 한 번에 설명하지 않았다. 경로 질문에는 해당 부분만 답하며
전체 실행 흐름과 모순을 다시 확인하지 않았다.

이를 실제 '기억상실', 모델 내부 장애, 컨텍스트 압축 또는 다른 시스템의 오류 때문이라고
확정할 내부 근거는 없다. 그런 설명으로 책임을 넘기지 않는다. 대화에서 확인되는
잘못은 내 작업 진행과 안내의 일관성 부족이다.

### 결과와 책임

- 사용자는 정상 자동 실행과 터미널 종료까지 오류인지 재확인해야 했다.
- 앱 없는 경로로 진단 실행을 시도해 해당 시도에서는 로그를 얻지 못했다.
- 불필요한 폴더 확인/스크린샷/메시지 왕복이 늘고 원인 분석이 지연됐다.
- 첫 로그가13초에 끝난 원인을 이 안내 실패나 특정 사용자 행동으로 단정하지는 않는다.
- 두 번째 로그는 정상 수집됐다. 이제 기존 자료로 분석을 진행할 수 있으므로 추가 조작을
  반복 요구하지 않는다. 잘못된 안내의 책임은 나에게 있다.

### 재발 방지 기준

- 배포 안내와 진단 안내를 동일 실행 경로로 검토한다. 앱 위치에 의존하면 먼저 명시한다.
- 예상되는 화면/터미널/앱 동작과 성공 확인 방법을 한 번에 전달한다.
