# r56 — 반복 렌더 축소와 실제 조작 피드백 / 미완

## 판정·범위

착지 반복 렌더, 매달리기 등 선을 수정하고 Release 실행을 확인하라는 요청이다.
첫 Release 실행본에서 사용자가 **호버 아웃 끊김, 걸치기 준비 팔 바동거림 누락,
화면 경계 때문에 작업표시줄에 걸 수 없음**을 보고했다. 그 실행본은 불합격이다.
후속 후보의 자동 검사·저장 프레임 확인은 실제 조작 수락을 대신하지 않는다.
원화 PNG·grab bank, 설치본·기본 실행·Mac·배포·commit/push는 이번 작업에서 바꾸지 않았다.

## 원인과 변경

1. 접촉 측정은 알파128 이상 픽셀의 연속 행 구간을 사각형으로 묶었다. 구멍과
   외곽은 유지하며 동일 아핀 변환·아래2DIP 접촉 구간을 측정한다.
2. 발바닥 측정 전용 렌더는 필요한 아래 행만 읽는다. 위치 보정용 전체 그림을
   여러 번 만들던 흐름을 BeginPlatformFrame→상태 계산→발 측정→최종1회 렌더로
   묶었다. 펼침 소스 캐시, 동일 내부 픽셀 빠른 처리, 최대6개 행 작업자를 사용한다.
   기존 보간·샘플 수·착지20회 역변환 계산은 유지했다.
3. 매달리기 몸은 채우기 경로의 등 부분에 stroke 호출이 없었다. 같은 경로와
   기존 펜을 이어 그려 locomotion bank를 다시 생성했다. 몸 클릭은 기존 변형 중심으로
   맞췄고, 매달리기 해제는 기존120ms 가로 클립 방식의 연결 후보를 추가했다.
4. 고해상도 렌더의 조기 반환 뒤 `_huntVisualFrame`이 갱신되지 않아 호버 종료가
   중립 프레임을 복귀 기준으로 읽었다. 실제 표시한 프레임을 저장하도록 고쳤다.
   사냥 몸 압축 해제의 중간 byte 배열도 없앴다. 그 자체로 모든 끊김이 사라졌다는 뜻은 아니다.
5. 같은 조기 반환이 기존 PerchReadinessPresentation을 건너뛰었다. 머리 잡기 준비
   표시를 소스 해상도의 팔 파츠 회전으로 연결했다. 첫 후보는 예전 팔 좌표를 그대로
   써 움직임이 거의 보이지 않았고, 다음 후보는 흰 칼라/남은 선이 보였다. 직접 저장
   시트를 열어 발견한 뒤 r33 몸 좌표로 정렬하고 안쪽 선의 바깥 흰 여백을 분리했다.
   원화 파일을 다시 그리지 않았다. 다른 부위로 잡았을 때의 준비 표시 동등성은 미검증이다.
6. 화면 제한은 바꾸지 않았다. 기존 설계는 잡은 몸 전체가 화면을 벗어나지 않게 하고,
   작업표시줄 진입 구간을 그 제한 안으로 옮긴다. 합성 실제 루프에서 세 크기 모두
   준비→놓기→붙기가 됐으므로 사용자 환경의 실패 원인을 화면 제한이라고 확정할 수 없다.
   명시적 진단 실행에만100ms 간격으로 위치·발판·준비 상태를 기록하도록 추가했다.

## 검사와 성능 근거

증거 루트: `artifacts/runtime-performance-20261018-r56/`.

- 초기 접촉/루프24개, 수정 후 발바닥/루프10개 통과. 렌더 지연 중 초기 Source layout이
  없어5개 실패했던 시도는 UpdateLayout 복구 후 재검사했다. 실패를 성공으로 세지 않는다.
- `r56-combined.trx`: 사용자 피드백 전 관련189개 통과. 이것만으로 실제 조작 결함을 찾지 못했다.
- `r56-feedback-combined.trx`: 피드백 수정 후 관련195개 통과. 전체 앱 테스트가 아니다.
- `r56-hover-supported.trx`: 고정 바닥에 완전히 착지한 뒤 호버 종료3개 통과.
  초기 호버 검사에는 움직이는 테스트 발판 때문에 착지 압축이 섞여 있었다. 실제 바닥으로
  바꾸고 모든 복귀 tick이 Supported인지 확인했다. 최종 검사는 그 조건을 사용한다.
- `r56-cue-edge.trx`: 1/1.25/1.5배에서 실제 PetLoop·Presenter와 합성 마우스/발판으로
  화면 안 커서→작업표시줄 준비→팔 프레임 변화→놓기→Attached를 검사해3개 통과.
- `final-loop`의480장과 r55 `loop-release-final`의 같은480장 PNG SHA256이 모두 같다.
  이것은 해당 잡기·낙하·착지 표본의 최적화 전후 동일성이며 새 팔/호버 동작의 동일성 증거는 아니다.
- r33 머리 `12d403f3…84edf`, 몸 `53474e7c…648a`, grab bank `f3281baf…a04` SHA256 유지.
- `git diff --check` 오류 없음. 저장소 기존 파일의 LF/CRLF 안내는 있었다.

## 실제 실행·도구 경계

- 첫 정상 투명 Release 후보 `live-release-app`을1.5배로 실행했다. `live-transparent.json`은
  60,068ms 동안 WPF callback4,424개, 실제 전달된 눌림7개(볼1/Body6)를 기록했다.
  초기10개 제외 callback 간격 중앙값12.90ms/p95 28.52ms/최대58.40ms이다.
  WPF callback 간격은 GPU/모니터 표시 FPS가 아니다. 사용자가 위 세 결함을 보고했다.
- native 도구는 진단 창의 UIA 텍스트를 읽었으나 스크린샷은 타임아웃이었다.
  투명/불투명 진단 창 모두 실패했으므로 투명 창만 원인이라고 확정하지 않는다.
  에이전트가 실제 마우스를 드래그하거나 실제 동작 영상을 관찰한 증거는 없다.
- 앞선 r56 진단/첫 정상 후보 프로세스는 정확한 경로를 확인한 뒤 종료했다.
- 후속 `feedback-release-app` Release publish 성공. PID22352로1.5배 실행하고
  `feedback-native.json`을 기록하도록 했다. 사용자에게 호버 종료·창/작업표시줄 준비·
  놓기·등 선 재확인을 요청했다. 설치본이 아닌 별도 검사본이며 후속 실제 사용자
  조작 결과는 아직 없다.

## 직접 본 저장 프레임

`feedback-index.json`에 묶음별 파일명이 있다. 최종 `review-{1,1.25,1.5}-`
hover0/16, flutter0, attach0/16의15개 시트를 직접 열었다. 호버32·팔16·붙기20장씩,
총204장의 저장 표본이다. 호버는 중간 몸 복귀를 거치고, 팔은 주기 중 각도가 바뀌며,
등 경계 stroke가 유지되는 것을 이 표본에서 확인했다. 실시간 재생·다른 방향/회전·모든
진입 상태의 시각 통과라는 뜻은 아니다. 초기 좌표/흰 여백 후보는 불합격으로 교정했다.
별도로 r33 몸 좌표 격자와 원본09도 열어 확인했다.

## 남은 문제 / 다음

1. 후속 Release 실제 호버 종료 지연, 창/작업표시줄 준비 표시와 붙기를 확인한다.
   실패하면 새 위치·접촉 로그로 자동 재현과의 차이를 좁힌다. 화면 제한을 임의로 풀지 않는다.
2. 1.5배 느린 tick, 새 팔 표시의 지속 부하, 장시간 실제 입력은 미완이다.
3. r55의 중간 눈감기, 매달리기 상단 접촉 상수43, 일반 자세→잡기 시간,
   볼·모든 상태 전환의 전체 시각 동등성은 이번 검사로 닫지 않는다.
4. 소스 원화 보존과 기존 완료 기준 유지. 설치 교체·전체 완료·배포 선언 금지.

작업 방식은 joewrks-pixel-art의 프로젝트 원화/증거 경계와 computer-use의 native
입력·캡처 경계를 따랐다. 기존 부분 알파·샘플러 계약을 일반 픽셀팔레트 규칙으로 바꾸지 않았다.
